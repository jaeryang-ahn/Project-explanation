# MOA — 민감 건강 데이터를 다루는 백엔드

무엇을 저장할지보다, 무엇을 저장하지 않을지를 먼저 정한 설계

## 개요

MOA는 고령층의 음성과 건강 대화를 분석해 파킨슨병·치매·당뇨의 이상 징후를 잡아내는 서비스다. 나는 백엔드 초기 구조를 세우고, DB 스키마와 인증을 설계·구현했다.

## 1. 인증을 우리 DB가 들지 않기로 한 결정

password 컬럼을 스키마에서 없애기

### 문제

회원 인증을 붙이려면 비밀번호를 어딘가에 둬야 한다. MOA는 고령층의 음성·건강 데이터를 다루는 서비스라, 회원 정보가 새면 그대로 사용자의 가장 민감한 정보로 이어진다. 인증 정보를 우리 DB에 둘지부터 정해야 했다.

### 판단

두 방식을 놓고 비교했다.

**A. 자체 회원 테이블에 비밀번호 해시를 저장하고 직접 인증 처리**
- 얻는 것: 인증 흐름 전체를 우리가 통제한다.
- 잃는 것: 비밀번호를 우리 DB가 직접 들고 있어야 한다. 해싱·솔팅·토큰 발급·만료를 직접 구현하고 유지해야 하고, 회원 테이블이 유출되면 인증 정보까지 함께 샌다. 지킬 것이 하나 늘어난다.

**B. 인증을 Supabase Auth에 위임하고, 서버는 발급된 JWT만 검증**
- 얻는 것: 비밀번호가 우리 DB에 존재하지 않는다. 회원 테이블에서 password 컬럼 자체를 없앨 수 있어, DB가 유출돼도 인증 정보는 새지 않는다.
- 잃는 것: 외부 인증 제공자에 의존한다.

기준은 "유출됐을 때 무엇이 새는가"였다. 민감 데이터를 다루는 서비스에서, 우리가 아예 안 가진 데이터는 샐 수 없다. 인증을 직접 통제해서 얻는 이점보다, 비밀번호를 안 갖는 데서 오는 안전이 크다고 봤다. B를 택해 인증을 Supabase Auth에 맡기고, 서버는 요청에 실린 JWT를 검증하는 역할만 하게 했다.

### 결과

`guardian`·`senior` 테이블의 PK를 Supabase `auth.users.id`로 잡고, password 컬럼을 두지 않았다. 서버는 비밀번호를 보관하지 않고 JWT 검증만 한다. 인증 관련 코드는 `core/security.py`와 `routes/auth.py`에 있다.

배운 점: 데이터를 덜 갖는 선택이 곧 공격 표면을 줄이는 일이었다.

## 2. 월간 리포트 — 통계를 저장할 것인가, 열 때 계산할 것인가

### 문제

월간 건강 리포트는 측정 횟수, 챗봇 대화 횟수, 이상 징후 발생 수, 질환별 평균 위험도를 담는다. 처음엔 이 값들을 리포트 테이블에 저장하려 했다. 곧 허점이 보였다. 원본 측정값이 리포트 생성 이후에 더 쌓이거나 수정되면, 저장해 둔 리포트 숫자는 옛날 값으로 굳어 원본과 어긋난다.

### 판단

두 방식을 비교했다.

**A. 리포트 생성 시점에 통계를 계산해 리포트 테이블에 저장**
- 얻는 것: 리포트를 열 때 집계 연산이 없어 조회가 가볍다.
- 잃는 것: 원본이 갱신되면 리포트 값이 원본과 어긋난다. 정합성을 맞추려면 원본이 바뀔 때마다 관련 리포트를 재계산하는 트리거를 빠짐없이 걸어야 하고, 그 순간 복잡도가 올라간다.

**B. 리포트 테이블엔 메타데이터만 두고, 수치는 조회 시점에 원본에서 집계**
- 얻는 것: 원본이 유일한 진실 소스가 된다. 원본이 바뀌든 대화가 쌓이든, 리포트는 언제 열어도 최신 값과 일치한다.
- 잃는 것: 리포트를 열 때마다 집계 연산이 돈다. 조회 성능이 관건이 된다.

건강 데이터는 나중에 측정값이 추가·수정될 여지가 크다고 봤다. 이 상황에서 A는 "불일치를 감수하거나, 재계산 트리거를 완벽히 관리하거나" 둘 중 하나를 강요한다. 정합성이 깨지면 사용자가 보는 리포트를 믿을 수 없게 되므로, 조회 비용을 지불하더라도 B를 택했다.

집계 방식도 정했다. 음성 수치 데이터와 대화 텍스트는 목적이 다른 데이터로 보고, 두 테이블을 JOIN하지 않기로 했다. `senior_id` 기준으로 각각 집계한 뒤 애플리케이션 코드에서 합친다. 이렇게 두면 나중에 대화 데이터를 별도 DB로 떼어낼 때 리포트 로직을 건드리지 않아도 된다.

### 결과

리포트 테이블(`monthly_report`)에는 `pdf_url` 같은 메타데이터만 남겼다. 실제 수치는 사용자가 리포트를 여는 순간 원본 테이블에서 집계해 내려준다. 이 설계 결정을 내가 했고, 집계 서비스(`services/monthly_stats.py`) 구현은 팀원(Gahyoung-Kim)이 이 스키마 위에서 맡았다.

배운 점: 무엇을 저장하느냐만큼, 무엇을 저장하지 않고 조회 시점에 계산하느냐가 정합성 설계였다.

## 3. 세션이 실제보다 몇 배 많던 문제

저장 코드가 아니라 요청을 의심하기

### 문제

챗봇 데이터를 보다가 저장된 세션 수가 실제 대화보다 몇 배 많은 걸 발견했다. 세션 하나의 지속 시간도 1~2초로 비정상적으로 짧았다.

### 판단

증상만 보면 서버의 세션 저장 코드를 고치고 싶었다. 데이터가 잘못 쌓일 땐 저장하는 쪽부터 의심하는 게 순서라 보고, 서버 적재 로직부터 확인했다.

서버 로직은 세션 ID가 있으면 기존 세션에 이어 붙이고, 없으면 새로 만드는 구조였다. 문제가 없었다. 서버는 요청받은 대로 저장하고 있었고, 원인은 요청 자체에 세션 ID가 빠진 것이었다. 클라이언트를 따라가니 세션 ID가 요청마다 초기화되고 있었다. 고쳐야 할 곳은 서버 저장 코드가 아니라 세션 ID를 유지하는 쪽이었다.

### 결과

세션 ID가 대화 전 구간에서 유지되도록 초기 원인을 잡아 고쳤다. 한 대화가 단일 세션으로 쌓였고, 세션 지속 시간이 1~2초에서 1분 이상으로 정상화됐다. 이후 파생된 세션 오류는 팀원(Gahyoung-Kim)이 이어받아 처리했다.

배운 점: 데이터가 잘못 쌓일 때, 증상이 나타난 곳(저장)과 원인이 있는 곳(요청)이 다를 수 있다. 저장하는 쪽부터 의심하되, 코드부터 고치지 않았다.

## 데이터 최소 저장 원칙 (스키마 전반)

위 판단을 관통하는 원칙은 "원본을 그대로 쌓지 않는다"였고, 이 원칙은 내가 주 저자인 `models/models.py`에 스키마로 남아 있다.

- 원본 음성 파일은 어떤 테이블에도 저장하지 않는다. AI 모델이 추출한 음향 수치 벡터만 적재한다. (벡터 추출은 다른 팀원 담당)
- 음성 수치(`voice_feature`)와 대화(`chat_session`)는 목적이 다른 데이터라 테이블을 분리하고, 나중에 대화 DB를 떼어낼 것을 대비해 둘 사이에 외래키를 걸지 않았다.
- 회원 테이블에 password 컬럼을 두지 않았다.
- 스키마 변경은 SQLAlchemy와 Alembic 마이그레이션으로 버전 관리했다.
- 복약·리포트처럼 정해진 시각에 도는 작업은 APScheduler로 스케줄링했다.

전체 테이블 수: 18개
